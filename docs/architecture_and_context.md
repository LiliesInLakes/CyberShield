# APK Sentinel — Project Context & Architecture Master Document

**Date:** July 21, 2026
**Context:** PSB Cybersecurity, Fraud & AI Hackathon 2026
**Objective:** Fortify the APK Sentinel GenAI-driven Android malware analysis pipeline with a focus on the Indian BFSI (Banking, Financial Services, and Insurance) threat landscape.

---

## 1. Project Overview & Philosophy

APK Sentinel is designed as a 7-layer evidence-driven pipeline to detect Android malware, specifically targeting banking trojans, SMS stealers, and impersonation attempts prevalent in the Indian ecosystem (e.g., Drinik, SOVA clones). 

**Core Design Principles:**
- **Evidence First:** LLMs (at L5/L6) do not analyze code directly. Instead, they read standardized, deterministic evidence generated by L0 (Triage) and L1/L2 (Static/Dynamic engines).
- **On-Premise / Isolated Execution:** The system must function entirely offline. External APIs (VirusTotal, MalwareBazaar, Google Vision) are strictly opt-in and fail gracefully if unreachable.
- **Continuous Analyst Feedback:** The system is designed to grow smarter over time via analyst feedback workflows (`cert_registry.py`, `yara_feedback.py`), avoiding the brittleness of static ML models.

---

## 2. Pipeline Architecture (Implemented Layers)

### L0: Ingestion & Triage (`L0/ingest.py`)
Acts as the gatekeeper. It processes the raw APK and outputs `evidence.json`.
- **Fingerprinting & Hashes:** Computes MD5, SHA1, SHA256.
- **Manifest Extraction:** Pulls package name, permissions, and app labels.
- **Impersonation Check (The Whitelist):** Uses `bank_whitelist.json` (39+ Indian banks, UPI platforms, and Gov apps). It checks package name matching, label similarity (including regional `alt_labels` like Hindi translations), and computes a perceptual hash (`pHash`) of the app icon to detect visual impersonation.
- **Certificate Analysis ("Innocent Until Proven Guilty"):** 
  - *Context:* We cannot maintain a list of *every* legitimate bank certificate.
  - *Logic:* 
    - Cert in whitelist = Strong Positive (+0.9).
    - Unknown cert = Neutral (0.0). The absence of evidence is not evidence of malware.
    - Self-signed cert on an app claiming to be a bank = Critical Red Flag (-0.9).
- **Reputation:** Local threat cache lookup, falling back to VirusTotal/MalwareBazaar if API keys are present.

### L1: Static Analysis (`L1/l1.py`)
Dispatches the APK to appropriate engines based on L0 routing, outputting a standardized `L1Report` containing `L1Finding` objects.
- **Jadx Engine (`jadx_analyze.py`):** Decompiles Dalvik bytecode to Java source and scans it using YARA.
- **Ghidra Engine (`ghidra_analyze.py`):** Extracts native `.so` libraries and runs headless Ghidra to extract strings and identify JNI payload structures.
- **YARA Engine (`yara_scan.py`):** The core intelligence engine. Runs raw APK scans (for structures/droppers) and source-level scans (for behavioral patterns).

### The Schema (`L1/schema.py`)
All L1 engines must emit uniform data so that L2 (Dynamic Analysis) and L5 (LLM Scoring) don't need to know *how* a threat was found.
- **ObservationSource:** `INFERRED` (Static analysis), `OBSERVED` (Runtime/Dynamic), `CONFIRMED` (Analyst verified).
- **MITRE ATT&CK Mapping:** Every finding category (e.g., `SMS_INTERCEPT`, `OVERLAY`) is mapped to a specific MITRE T-Code (e.g., `T1636.004`, `T1417.002`).

## 3. The Indian Threat Landscape Integration

A massive focus was placed on tailoring this tool for the Indian ecosystem, heavily influenced by threats like **Drinik**.

### The Whitelist Expansion (`bank_whitelist.json`)
Expanded from 4 generic entries to **39 highly-targeted entities**:
- All 12 Public Sector Banks (SBI, PNB, BOI, etc.).
- Major Private Banks (HDFC, ICICI, Axis).
- UPI Platforms (PhonePe, GPay, Paytm, BHIM).
- **Government Lures:** Drinik heavily targets Income Tax (ITR), UMANG, and DigiLocker. These are now explicitly protected.

### India-Specific YARA Rules
1. **`apk_india_banking.yar`:**
   - **Drinik/ITR Impersonation:** Looks for "iAssist", "tax refund", combined with Accessibility Service abuse and Firebase C2.
   - **UPI Targeting:** Detects intents calling `upi://` combined with overlays and package targets like `com.phonepe.app`.
   - **Indian SMS OTP Stealers:** Looks for SMS interception code specifically hunting for Indian sender IDs like `SBIINB`, `HDFCBK`, `BOIIND`.
   - **Fake Bank / KYC Lures:** Detects strings like "KYC", "Aadhaar", "PAN card blocked" alongside WebView phishing patterns.

2. **`apk_clipboard_notification.yar`:**
   - Detects clipboard hijackers hunting for Crypto Wallets and UPI IDs.
   - Detects Notification Listener abuse (a common alternative to SMS permissions for stealing OTPs).
   - Detects Telegram/WhatsApp Bot C2 channels (highly prevalent in cheap Indian malware).

## 4. Continuous Analyst Workflows (The Feedback Loop)

To prevent the tool from degrading as attackers pivot, we built analyst-driven feedback loops.

1. **The Certificate Registry (`L0/cert_registry.py`)**
   - An append-only CLI tool. When an analyst verifies an official bank APK from the Play Store, they run this tool to extract the cert `sha256` and icon `pHash`, injecting it into the whitelist. The system's impersonation detection grows stronger over time.

2. **The YARA Feedback Loop (`L1/yara_feedback.py`)**
   - When an analyst reviews L1 findings, they can use this CLI to log a `TP` (True Positive) or `FP` (False Positive). 
   - If the analyst finds a threat that L1 missed, they log a `missed` detection along with the suspicious strings they found. The tool automatically generates a **YARA rule stub** for the team to review and add.

## 5. Portability & Isolation

**The Pivot from Windows to OS-Agnostic:**
Initially, the prototype had hardcoded Windows paths (`D:\BOI\...`). This was fundamentally incompatible with secure, reproducible malware analysis.

- **`setup_env.sh` & `Dockerfile`:** The entire pipeline now runs in an isolated Python virtual environment or Docker container.
- **Environment Variables:** External tools like Ghidra and Jadx, and their respective Java environments (JDK 17 and JDK 21), are resolved dynamically via `os.environ` (e.g., `JADX_DIR`, `GHIDRA_HOME`).

---

## Summary of Impact
The transition made in this phase elevated APK Sentinel from a simple script to a **modular, context-aware, and auditable analysis platform**. It natively understands the difference between a generic banking trojan and one specifically hunting for Indian Aadhaar data, and it does so in a way that is easily consumable by the upcoming LLM aggregation layers.
